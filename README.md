# re-forge

実務コードを解読し、自分の手で再構築する deliberate practice リポジトリ。

## コンセプト

- **forge** — 実務コードから抽出した1つのパターン・テーマ
- **heat** — 同じパターンを抽象度を上げながら実装する段階(heat-1 → heat-2 → heat-3)

## 学習目的

re-forge の本質は **「責務を自分で言語化する訓練」** だ。コードを書けるようになることは副産物にすぎない。

このため、各 heat は2段階で進める。

### 段階A: 仕様起こし

1. `heat-N/problem.md` を読む。**仕様書・チケット**（受け入れ条件が一次ソース）。
2. `heat-N/kata.ts` を開く。関数シグネチャと JSDoc の空枠だけがある。
3. **チケットを蒸留して JSDoc を書く。** 下記「JSDoc の書き方」を参照。チケットに書き方は載っていない。
4. 受け入れ条件に沿って実装する。

この段階では `spec.md` と `kata.test.ts` を**開かない**こと。仕様（何をするか）ではなく、実装の判断（どう書くか）を自分の言葉で固定する訓練が目的。

### 段階B: 答え合わせ

5. `heat-N/spec.md` を開く。お題側が想定した仕様と、設計の解説が書いてある。
6. **自分の JSDoc と突き合わせる。**
   - 1ヵ月後に読んで「何のための関数か」分かるか
   - 型に出ない注意を書き漏らしていないか
   - 書きすぎていないか（チェックリストの写経になっていないか）
7. `npx vitest <パス>` を実行する。
8. テストで落ちた箇所を直しつつ、契約も更新する。

### 解答との比較

行き詰まったら `heat-N/kata.solution.ts` を開く。写経より意図の理解を優先。

## ディレクトリ構成

```
re-forge/
└── forge-NN-name/
    ├── README.md           ← forge全体の概要と heat 構成
    └── heat-N/
        ├── problem.md      ← チケット（受け入れ条件・型）(段階A)
        ├── spec.md         ← 設計解説・観察ポイント(段階B)
        ├── kata.ts         ← 関数シグネチャと軽量JSDoc雛形
        ├── kata.test.ts    ← テスト(段階Bまで開かない)
        └── kata.solution.ts ← 解答(行き詰まったとき用)
```

## セットアップ

```bash
npm install
```

## テストの実行

### 特定の forge だけ走らせる(推奨)

```bash
npx vitest forge-01-closure
```

### 特定の heat だけ走らせる

```bash
npx vitest forge-01-closure/heat-1
```

### 全テストを走らせる

```bash
npm test
```

### 1回だけ実行(watch なし)

```bash
npm run test:run
```

## JSDoc の書き方

判定基準は1つ。**1ヵ月後の自分が、実装を全部読まなくても「何のための関数か」分かるか。**

[TSDoc](https://api-extractor.com/pages/tsdoc/doc_comment_syntax/) でも本文（summary）は短く、詳細は必要なときだけ足す、が公式の形。見出しを埋める宿題ではない。

### 書くこと（2層）

1. **1文目（必須）** — 何のための関数か。
   - 「いつ・誰が・何のために呼ぶか」が分かればよい
   - 関数名の言い換えは禁止（`patchState` に「state を patch する」はダメ）
   - 「なぜこの関数を切り出したか」も、ここに吸収する。切り出した理由が1文目から読めれば十分
2. **2文目以降（任意）** — 別のやり方もできたが、こう決めたこと。
   - テスト: **別のエンジニアが逆に実装しそうか？** はいなら書く
   - 関数の中で何が起きるか（ループの書き方、呼び順）は書かない。それはコード
   - 無ければこの行ごと消す

`【意図】` `【契約】` のような見出しは使わない。実務のコメントに学習用の枠は残さない。

### 良い例 / 悪い例

悪い（枠を埋めた。1ヵ月後に読めない）:

```ts
/**
 * 【意図】呼ぶ側にとっての価値を1〜2行で
 *  - 状態を更新する
 * 【契約】
 *  - 正常時: パッチしたキーだけ書き換わる
 *  - 困った入力: 空パッチでは何も変えない
 *  - しないこと: 新しいオブジェクトを返さない
 *  - 暗黙の決め: undefined はスキップ
 */
```

良い（何のためか分かり、裏切りポイントだけ残っている）:

```ts
/**
 * ピッカーの選択状態を、変えた軸だけ上書きする。
 *
 * 渡したオブジェクトをその場で書き換える。値が `undefined` のキーは触らず、空文字は書き込む。
 */
```

### 迷ったときのチェックリスト

4問に答える作業は残してよい。ただし **答えを JSDoc に並べない。** 2文目に残すことがあるかを確認するだけ。

| 確認 | JSDoc に残すか |
|------|----------------|
| 型のシグネチャで分かる | 書かない |
| 関数名を言い換えただけ | 書かない |
| なぜこの関数を切り出したか | 1文目に含める。2文目にはしない |
| 中でキーをどう回すか、呼び順 | 書かない（実装） |
| 別のエンジニアが逆に実装しそうな決め（副作用・`undefined` の意味） | 2文目に書く |
| なぜこの引数の形か（DI など） | 本文に混ぜない。必要なら実装の近くに1行 |

heat-3 オーケストレータでは、この関数だけが決めること（いつ `null` か、いつ打ち切るか）だけを2文目に残す。

## AI向け: 新しい forge を作るときの仕様

このリポジトリで新しい forge を追加する際は、以下の構造とルールに従うこと。

### ファイル構成(必須)

各 heat に以下の5ファイルを置く。

```
heat-N/
├── problem.md         # 段階Aで読む。チケット（背景・受け入れ条件・型）
├── spec.md            # 段階Bで読む。想定仕様と設計解説を書く
├── kata.ts            # 関数シグネチャと軽量JSDoc雛形のみ
├── kata.test.ts       # テスト(内容は spec.md と整合させる)
└── kata.solution.ts   # 解答
```

forge ディレクトリ直下にも `README.md` を置き、heat 構成と実務コードとの対応を書く。

### problem.md の書き方

含めるべきセクション（チケット型）:

1. **背景** — 誰が、いつ、なぜ必要か（実コードの文脈）
2. **やること** — 何を実装するか（1〜2文）
3. **受け入れ条件** — 業務側と握った挙動（対象・スキップ条件・値の決め方・戻り値）。テストの一次ソース
4. **型** — 関数シグネチャ
5. **実装者が決めること** — 受け入れ条件を満たす範囲で任せる判断。**答えは書かない**
6. **進め方** — 段階A→Bの手順。JSDoc は「チケットを蒸留する」とだけ書き、書き方の問いかけは置かない

**書いてはいけないこと:**

- ✗ 受け入れ条件を spec.md や kata.test.ts 側に隠す（一次ソースを problem.md に寄せる）
- ✗ 実装の手順・内部アルゴリズムの写経（関数の責務がぼやける）
- ✗ JSDoc の書き方・4問・「2文目にこれを書け」を problem.md に置く（蒸留の練習が壊れる）

受け入れ条件は problem.md に書き、spec.md は「設計の解説・代替案・観察ポイント」を担う。

### spec.md の書き方

含めるべきセクション:

1. **仕様の参照** — 受け入れ条件は `problem.md` が一次ソースであることを明記（必要なら要点を短く再掲してもよいが、二重管理は避ける）
2. **自分の JSDoc と比較する観点** — 1ヵ月後に読めるか、型に出ない注意を残したか、書きすぎていないか
3. **観察ポイント** — そこに含まれる設計パターンの解説（なぜその形が保守しやすいか等）

「正解」ではなく「**第三者の視点**」として機能させる。学習者の判断と突き合わせる対話の相手になるよう書く。

### kata.ts の書き方

```ts
// [heat-N] (簡潔なタイトル)
//
// 仕様は problem.md を参照。
// 行き詰まったら kata.solution.ts を参照。

// 型定義(必要なら)
export type Foo = { ... };

/**
 * （何のための関数か。1文。関数名の言い換えはしない）
 *
 * （別のやり方もできたが、こう決めたこと。無ければこの行は消す）
 */
export function xxx(...): ... {
  throw new Error("not implemented");
}
```

**重要なルール:**

- 仕様コメント(① ② ③ ...) を kata.ts に書かない。すべて problem.md と spec.md に分離する。
- JSDoc は2層の空枠だけ渡す。学習者が埋める。2文目の枠は、書くことが無ければ消す。
- 解答例を JSDoc に書かない。

### kata.solution.ts の書き方

最終的な実装コードと、必要なら短い解説コメント。JSDoc は最小限で良い。

### 設計判断の難所がある場合

heat の主題が「DI」や「非同期」など、設計判断の難所を含む場合は、problem.md の **「あなたが決めること」** セクションでその判断を学習者に明示的に投げる。

例:

> - なぜ `window.location` を直接呼ばずに引数で受けるか、自分なりの仮説を立ててから実装する

spec.md ではその判断の背後にある設計原則を解説する。
