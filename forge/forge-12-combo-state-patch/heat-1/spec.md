## 自分の契約と比較する観点

### 「truthy だけコピー」の意図

SKU テーブル上、軸が未設定の行はプロパティ自体が無いか空文字のことがある。**空文字を state に入れると `resolveSku` が「空文字で絞る」と解釈**し、意図しない未マッチになる。

`if (sku.ballDiameter)` は「値があるときだけ state に載せる」という**存在チェック**の省略形。

### wrapping を含めない理由

実務の `stateFromSku` は色・径・行数だけをピッカー state に載せる。包装（wrapping）は別 UI または後段で扱う。**変換関数の責務を「ピッカー3軸だけ」に絞る**判断。

### 新規オブジェクトを返す理由

呼び出し側が `const state = stateFromSku(row)` で保持し、以降 `patchState` で更新する。参照共有すると更新が意図せず波及する。**変換 = 新規生成** が安全。

## 観察ポイント: 変換関数の形

```
VariationSku (テーブル行)  →  stateFromSku  →  ComboState (UI 状態)
```

入力型と出力型が違うとき、**何を落とし、何を必須にするか**を最初に決めるのがロジック設計の起点。この heat はその最小単位。
