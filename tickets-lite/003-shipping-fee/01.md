# [003/01] 送料の決定

## 背景

カートと商品詳細ページ（PDP）で、配送先の地域・商品合計・配送オプションから送料を出している。地域ごとの基本料はテンプレートの PHP 配列、送料無料のしきい値は jQuery の定数、離島・クール便の加算はカート側の PHP と、同じルールが3箇所に分かれている。その結果「あと○円で送料無料」の表示とカートの送料がずれる問い合わせが続いている。

送料と「あと○円で送料無料」を決める処理を純関数に切り出す。

## 要求（業務の言葉）

- 「送料は配送先の地域ごとに決まっている基本料。商品合計がしきい値以上なら基本料は無料にしてほしい」
- 「離島とクール便は加算。送料無料の注文でも加算分はいただく」
- 「送料無料まであといくらか、カートに出したい。無料になっていれば 0 でいい」
- 「ありえない地域や合計金額が来たら、金額を出さずエラー扱いにしてほしい」

## 受け入れ条件

`calculateShippingFee(order, policy)` は次の順で判定し、いずれか1つの結果を返す。

| 順 | 条件 | 結果 |
|---|---|---|
| 1 | `order.subtotal` が 0 未満、**または** `order.region` が `policy.baseFeeByRegion` のキーに存在しない | `{ status: "invalid" }` |
| 2 | それ以外 | `{ status: "ok", fee, remainingForFree }` |

`fee` の決め方:

- 基本料 = `policy.baseFeeByRegion[order.region]`
- `order.subtotal >= policy.freeShippingThreshold` なら基本料は **免除**（0 になる）。ちょうど同額も免除
- 加算 = （`order.isRemoteIsland` なら `policy.remoteIslandSurcharge`）+（`order.requiresCool` なら `policy.coolSurcharge`）
- 基本料が免除されても **加算は残る**
- `fee` = 基本料（免除なら 0）+ 加算

`remainingForFree` の決め方:

- 基本料が免除されているなら `0`
- 免除されていないなら `policy.freeShippingThreshold - order.subtotal`

補足:

- 金額は整数（円）で来る。小数・`NaN`・`Infinity` は考えない
- `order` `policy` を変更しない。例外を投げない

## 境界

`solution.ts` から `calculateShippingFee` を export する。型の名前・定義場所は自由（`solution.ts` 内で定義する）。

```ts
type ShippingOrder = {
  subtotal: number;
  region: string;
  isRemoteIsland: boolean;
  requiresCool: boolean;
};
type ShippingPolicy = {
  baseFeeByRegion: Record<string, number>;
  freeShippingThreshold: number;
  remoteIslandSurcharge: number;
  coolSurcharge: number;
};
type ShippingFeeResult =
  | { status: "ok"; fee: number; remainingForFree: number }
  | { status: "invalid" };

export function calculateShippingFee(
  order: ShippingOrder,
  policy: ShippingPolicy,
): ShippingFeeResult;
```

## 入出力例

サイト設定（テストと同じ）:

| 項目 | 値 |
|---|---|
| `baseFeeByRegion` | kanto: 600 / hokkaido: 1200 / okinawa: 1500 |
| `freeShippingThreshold` | 5000 |
| `remoteIslandSurcharge` | 500 |
| `coolSurcharge` | 300 |

| subtotal | region | 離島 | クール | 期待結果 |
|---|---|---|---|---|
| 3000 | kanto | − | − | `ok`, fee `600`, remainingForFree `2000` |
| 5000 | kanto | − | − | `ok`, fee `0`, remainingForFree `0`（ちょうどしきい値で免除） |
| 8000 | kanto | ○ | ○ | `ok`, fee `800`, remainingForFree `0`（免除されても加算 500 + 300 は残る） |
| 3000 | hokkaido | − | ○ | `ok`, fee `1500`, remainingForFree `2000` |
| 4999 | okinawa | ○ | − | `ok`, fee `2000`, remainingForFree `1` |
| 0 | kanto | − | − | `ok`, fee `600`, remainingForFree `5000` |
| 3000 | tohoku | − | − | `invalid`（テーブルに無い地域） |
| −1 | kanto | − | − | `invalid` |

## やらないこと

- 送料の内訳（基本料と加算の別）は返さない（数値2つだけ）
- 税は扱わない（テーブルの金額は表示用の確定額とみなす）
- 都道府県から地域への変換はしない（`region` は変換済みで来る）
- 配送日時指定・複数配送先・複数個口は扱わない
- `policy` の値の妥当性（負の料金、しきい値 0 など）は検証しない（管理画面側で保証）

## 実装者が考えること（コードには出ないが、答えを持つこと）

入力の型（`ShippingOrder` `ShippingPolicy`）はカートとサイト設定が決めている環境の事実で、あなたが設計するものではない。一方、戻り値の型（`ShippingFeeResult`）は呼び出し側と握った **契約** であって自明ではない。テストを決定的にするため形は固定してあるが、実装する前に次に自分の答えを持つ。

- `fee` と `remainingForFree` を同じ結果に載せているのはなぜか。送料を返す関数と「あと○円」を返す関数に分けた場合、2つの関数が **共有する判断** は何か。それを別々に書いたとき何が起きうるか
- 「免除されても加算は残る」を、コードのどこで・どの順で表現するか。免除を「`fee` を 0 にする」と書いた場合と「基本料を 0 にする」と書いた場合で、加算の扱いはどう変わるか
- `invalid` を例外ではなく戻り値にしているのは 001/002 と同じ問い。ただし今回は「テーブルに無い地域」というサイト設定への参照の失敗を invalid にしている。これは入力（`order`）の問題か、設定（`policy`）の問題か。呼び出し側がそれを区別する必要があるとしたら、どこで区別するか
- この形で困る変更は何か（例: 「クール便加算だけ別行で表示したい」「無料になった理由をバッジに出したい」と言われたら）
