# [001/01] SKU 検索

## 背景

商品詳細ページ（PDP）で、ユーザーが選んだ「色」「直径」「行（row）」の組み合わせから SKU を探す。在庫マスタには全組み合わせが登録されているわけではなく、無い組み合わせのときは近い直径の候補を出して離脱を防ぎたい。

現状は PDP の jQuery に `$.grep` が3回ネストして書かれており、カート側にも似たコードがある。ロジックを純関数に切り出す。

## 要求（業務の言葉）

- 「選んだ組み合わせがあれば、その SKU をそのまま出してほしい」
- 「無ければ、色と行は同じで直径が近いものを3つまで出してほしい。近い順で」
- 「ありえない色や行が来たら（改造 URL など）、候補を出すのではなくエラー扱いにしてほしい」

## 受け入れ条件

`findSku(query, inventory)` は次の順で判定し、いずれか1つの結果を返す。

| 順 | 条件 | 結果 |
|---|---|---|
| 1 | `query.color` が `inventory` のどのレコードにも登場しない、**または** `query.row` がどのレコードにも登場しない | `{ status: "invalid" }` |
| 2 | `color` `diameter` `row` が完全一致するレコードがある | `{ status: "exact", sku }` |
| 3 | それ以外 | `{ status: "suggestions", candidates }` |

`candidates` の決め方:

- `color` と `row` が一致するレコードだけを対象にする
- `|diameter - query.diameter|` の **小さい順**。差が同じなら **直径の小さい順**
- 最大3件。対象が無ければ `[]`
- 要素は `sku` 文字列

補足:

- 同じ `(color, diameter, row)` が複数レコードに登録されることはない（マスタ側で保証）
- `inventory` の並び順に結果が依存しないこと
- `query` `inventory` を変更しない（`sort` の破壊的呼び出しに注意）。例外を投げない

## 境界

`solution.ts` から `findSku` を export する。型の名前・定義場所は自由（`solution.ts` 内で定義する）。

```ts
type SkuQuery = { color: string; diameter: number; row: string };
type InventoryItem = { sku: string; color: string; diameter: number; row: string };
type SkuSearchResult =
  | { status: "exact"; sku: string }
  | { status: "suggestions"; candidates: string[] }
  | { status: "invalid" };

export function findSku(query: SkuQuery, inventory: InventoryItem[]): SkuSearchResult;
```

## 入出力例

在庫マスタ（テストと同じ）:

| sku | color | diameter | row |
|---|---|---|---|
| R6A | red | 6 | row-A |
| R8A | red | 8 | row-A |
| R10A | red | 10 | row-A |
| R12A | red | 12 | row-A |
| R20A | red | 20 | row-A |
| R10B | red | 10 | row-B |
| G10A | green | 10 | row-A |

| query | 期待結果 |
|---|---|
| red / 10 / row-A | `exact`, `R10A` |
| red / 10 / row-A（R10A を除いたマスタ） | `suggestions`, `["R8A", "R12A", "R6A"]`（差 2, 2, 4。差2同士は直径の小さい R8A が先） |
| green / 20 / row-B | `suggestions`, `[]`（green も row-B も存在するが、green × row-B のレコードが無い） |
| blue / 10 / row-A | `invalid` |
| red / 10 / row-Z | `invalid` |

## やらないこと

- 直径以外（色・行）を変えた候補は出さない
- 在庫数・販売ステータスは見ない（マスタに載っていれば「ある」）
- マスタは配列で渡される。API・DB は考えない
- 大文字小文字の正規化はしない（完全一致）

## 実装者が考えること（コードには出ないが、答えを持つこと）

入力の型（`SkuQuery` `InventoryItem`）はマスタと PDP が決めている環境の事実で、あなたが設計するものではない。一方、戻り値の型（`SkuSearchResult`）は呼び出し側と握った **契約** であって自明ではない。テストを決定的にするため形は固定してあるが、実装する前に次に自分の答えを持つ。

- `invalid` を例外ではなく戻り値にしているのはなぜか。例外にした場合、呼び出し側（PDP の jQuery）はどう変わるか
- 候補ゼロを `suggestions: []` にし、4つ目のステータスを作らなかったのはなぜか。作った場合、呼び出し側の分岐はどう変わるか
- この形で困る変更は何か（例: 「なぜ invalid なのか（色が無いのか、行が無いのか）」を UI に表示したいと言われたら）
