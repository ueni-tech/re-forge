# tickets-lite

1チケット = **`NN.md`（チケット）+ `NN.test.ts`（判定）** の2ファイル。シリーズ = 1フォルダ + `solution.ts` 1つ。

```
tickets-lite/
├── 001-sku-search/      ← 探す・並べる・段階ごとに違う意味のフィールド
└── 002-price-display/   ← 計算・表示方針・基準額の差し替え
    ├── solution.ts      ← ここに書く。テストが import するのはこのファイルだけ
    ├── 01.md            ← 新規実装チケット
    ├── 01.test.ts
    ├── 02.md            ← 変更チケット。01 が緑になるまで開かない
    └── 02.test.ts
```

## やり方

1. `01.md` を読み、`solution.ts` を書く。内部の関数分割・型・命名は自由
   ```bash
   npx vitest run tickets-lite/001-sku-search/01
   # または
   npx vitest run tickets-lite/002-price-display/01
   ```
   パスはチケット番号まで指定する（フォルダ全体だと 02 のテスト名がログに出て内容が漏れる）
2. 緑になったら、下の **3つの問い** に答える（頭の中でよい）
3. AI にレビューを頼む（下の依頼文）
4. `02.md` を開く。**開く前に** 「触るファイル・関数・行数」を1行予測して `solution.ts` の末尾コメントに書く
5. 01 と 02 を同時に走らせて緑にする。`git diff --stat` で予測と比べる
   ```bash
   npx vitest run tickets-lite/001-sku-search
   # または
   npx vitest run tickets-lite/002-price-display
   ```

## 3つの問い（チケットが緑になるたびに）

1. **責務**: `solution.ts` の中に、いくつの「仕事」があるか。名詞で数える（判定、並べ替え、変換、組み立て…）。それぞれ別の関数になっているか、1つに混ざっているか。混ざっているなら理由は
2. **変更容易性**: 次に来そうな変更を1つ想像し、触る箇所を予測する。「1箇所」と答えられない変更があるなら、それは今の構造のどこが原因か
3. **テスト容易性**: 一番複雑な判定を、`findSku` を通さず単独で呼べるか。呼べないなら、困る場面があるか

変更チケット（02 以降）では加えて:

4. **予測は当たったか**: 触ると予測した箇所と実際に触った箇所の差。差が出たなら、01 のどの構造が見えていなかったか

## AI レビューの依頼文

```
tickets-lite/002-price-display/solution.ts をレビューしてください。チケットは同フォルダの 01.md です。
責務・凝集度・結合度・変更容易性・テスト容易性の観点で、
「問題点 → なぜ問題か → どんな変更が来たとき困るか → 代替案 → 代替案が劣る点」の順で書いてください。
完成コードは出さないでください。分割を提案するなら、なぜその数か、1つ少ないと何が起き、1つ多いと何が過剰かまで。
```

（シリーズが違うときはパスだけ読み替える）

## なぜテストだけでは足りないか

テストは振る舞いしか見ない。300行の1関数でも分割された実装でも同じテストが緑になる。設計の良し悪しは **次の変更が何行になるか** でしか測れない。だから 02 がある。02 を開く前に予測を書くのは、影響範囲を読む力を「予測と実績の差」として見えるようにするため。

## 出題者（AI）向け

- チケットは **背景 / 要求（業務の言葉）/ 受け入れ条件 / 境界（export する関数1つ）/ 入出力例 / やらないこと / 実装者が考えること** の7節。「作るもの」の列挙はしない（責務の切り方は答えだから）
- 境界は関数1つ。型は `NN.md` に書き、`solution.ts` 側で学習者が定義する。テストは関数しか import しない
- **入力の型は環境なので渡す。戻り値の型は契約なので渡すが、それは設計判断（エラー処理・状態の表現）を1つ奪っている。** 必ず「実装者が考えること」節を置き、なぜその形か・別の形なら呼び出し側がどう変わるかを問う
- テストは決定的に。複数の結果を許す `toContain([a, b])` は書かない。同値時の順序も仕様に書く
- 入力は `Object.freeze` して渡し、破壊的変更を検出する
- 02 は **境界を変えずに** 圧をかける（入力データにフィールドが増える、ルールが増える、順序が変わる）。01 のテストは緑のまま
- 03 以降は学習者の `solution.ts` を見てから書く
- 参考解は置かない。詰まったら AI に「ヒントだけ」と頼む
